3. Java & Concurrency

Q1. What is a Thread?

A thread is a lightweight unit of execution within a process. Multiple threads can execute tasks concurrently within the same application.

Interview: “A thread is a lightweight unit of execution within a process. Multiple threads can execute tasks concurrently and share process resources.”

Q2. What is a Thread Pool and why use it?

A thread pool manages reusable threads. Instead of creating a new thread for every task, tasks are submitted to the pool.

  • Reuses threads
  • Reduces thread-creation overhead
  • Controls concurrency and resource usage
ExecutorService executor = Executors.newFixedThreadPool(10);
executor.submit(() -> {
    // task
});

Interview: “A thread pool manages reusable threads to execute tasks efficiently and control the number of concurrent tasks.”

Q3. What is synchronized?

synchronized provides mutual exclusion for a monitor. For the same monitor, only one thread can execute the synchronized section at a time.

synchronized void withdraw(int amount) {
    balance -= amount;
}

Key point: It coordinates threads inside the JVM. It is not a distributed lock across multiple server instances.

Q4. What is volatile?

volatile guarantees visibility of writes to a variable across threads. It does not make compound operations atomic.

volatile boolean running = true;

Remember: volatile = visibility, not full thread safety.

Q5. synchronized vs Lock?
synchronizedSimple, language-level locking, automatic release when leaving the synchronized block/method.
Lock / ReentrantLockExplicit lock management and features such as tryLock() and interruptible locking.

Interview: “ReentrantLock gives more explicit and flexible control than synchronized, while synchronized is simpler for straightforward mutual exclusion.”

Q6. What is ConcurrentHashMap?

It is a thread-safe Map implementation designed for concurrent access. It provides better concurrency than simply synchronizing every access to a normal map.

Interview: “I would use ConcurrentHashMap when multiple threads need to access and update shared map data concurrently.”

Q7. What is a Race Condition?

A race condition happens when multiple threads access shared data concurrently and the result depends on execution timing.

int count = 0;

// Thread A and B both do:
count++;

// Expected: 2
// Possible result: 1

Solutions include synchronization, locks, atomic operations, thread-safe collections, database controls, or distributed locks depending on the problem.

Q8. What is a Deadlock?

A deadlock occurs when threads wait for locks held by each other, so none can continue.

Thread A: Lock 1 → waits for Lock 2
Thread B: Lock 2 → waits for Lock 1

Prevention: consistent lock ordering, minimizing nested locks, short lock duration, and mechanisms such as tryLock().

Q9. What is JVM Heap vs Stack?

Heap: shared memory area where objects are generally allocated and managed by garbage collection.

Stack: each thread has its own stack, containing method frames, local variables and execution state.

Interview: “The heap is shared among threads and stores objects, while each thread has its own stack for method execution and local state.”

4. Spring Boot & Spring Cloud

Q1. What is IoC?

Inversion of Control means object creation and dependency management are controlled by the Spring container rather than by application classes themselves.

Q2. What is Dependency Injection?

Dependencies are provided to a class instead of the class creating them itself.

@Service
class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}

Interview: “Dependency Injection improves loose coupling, testability, and maintainability.”

Q3. What are @Component, @Service and @Repository?
  • @Component — general Spring-managed component
  • @Service — service/business layer
  • @Repository — data-access layer

Controller handles HTTP concerns, Service handles business logic, Repository handles persistence.

Q5. What is @Transactional?

It defines a transaction boundary. Successful work can be committed; when a transaction fails according to rollback rules, changes can be rolled back.

Example: bank transfer or a critical ride-state update where multiple database changes must remain consistent.

Q6. How do you handle exceptions globally?

Use @RestControllerAdvice / exception handlers to return consistent API error responses.

    // @ExceptionHandler(...)
}
Q7. What is an API Gateway?

An API Gateway is a single entry point for clients. It can perform routing and cross-cutting concerns such as authentication, filtering and request management.

Q8. What are the advantages and disadvantages of microservices?

Advantages: independent deployment, independent scaling, service isolation, business-domain separation.

Disadvantages: network failures, distributed data consistency, observability complexity, deployment complexity and service-to-service communication.

5. Distributed Systems

Core scenario: Driver A and Driver B try to accept Ride #123 at the same time.

Q1. Why can't synchronized alone solve the two-driver problem?

Because synchronized coordinates threads within one JVM. In a distributed deployment:

Driver A → Server 1 / JVM 1
Driver B → Server 2 / JVM 2

The JVMs do not share the same monitor. A shared distributed mechanism is needed.

Q2. What is a Distributed Lock?

A distributed lock coordinates access to a shared resource across multiple application instances.

Driver A → Server 1 → Redis → acquire ride:123
Driver B → Server 2 → Redis → lock unavailable

Interview: “Because multiple instances can process the same ride concurrently, I could use a Redis-based distributed lock around the critical section.”

Q3. Is a Redis lock alone enough?

No. Treat the database as the source of truth for the ride state. Validate the current state and use a transaction/conditional update.

UPDATE rides
SET status = 'ACCEPTED', driver_id = ?
WHERE id = ?
  AND status = 'AVAILABLE';

If another request already accepted it, the second update affects zero rows.

Q4. What is Idempotency?

Idempotency means retrying the same logical request does not create repeated business effects.

POST /rides/123/accept
Idempotency-Key: abc123

First request processes and stores the result. A retry with the same key can return the stored result instead of performing the business operation again.

Remember: “Lock protects concurrent execution. Idempotency protects against duplicate/retry operations.”

Q5. What is Eventual Consistency?

In a distributed system, different components may temporarily have different states. After events are propagated and processed, they converge to a consistent state.

Ride Service
  ↓
MySQL: ACCEPTED
  ↓
Kafka event
  ↓
Notification Service
  ↓
Notification sent later

Core ride assignment may need strong consistency, while notifications/analytics can often tolerate eventual consistency.

Q6. Full answer: two drivers accept the same ride

“First, I would treat ride acceptance as a high-concurrency operation. Since multiple application instances may process the request, I could use a Redis-based distributed lock for the specific ride to prevent concurrent processing.

Then I would check the ride status in the database and update it only if it is still AVAILABLE. I would use a transaction or conditional update so the database remains the final source of truth.

I would also make the API idempotent, for example by using an idempotency key, so a client retry does not process the ride acceptance multiple times.

After successful acceptance, I could publish an event through Kafka for asynchronous work such as notifications or analytics. Those downstream services can use eventual consistency where exact immediate consistency is not required.”

Q3. What is cache invalidation?

When the underlying data changes, cached data may become stale. The application needs a strategy to invalidate, update, or expire the relevant cache.

Q4. What are cache penetration, breakdown and avalanche?
  • Penetration: requests repeatedly query keys that don't exist, potentially hitting the database.
  • Breakdown: a very popular key expires and many requests hit the database at once.
  • Avalanche: many cache keys expire together, causing a large database load spike.

7. Kafka

Q1. Why use Kafka?

Kafka supports asynchronous, event-driven communication and decouples producers from consumers. It can scale message processing and helps prevent one slow downstream service from blocking the entire business flow.

Your CV: You used Kafka in a financial/accounting system and implemented event-driven architecture.

Q2. Explain Topic, Partition, Producer, Consumer and Consumer Group.
Producer
   ↓
Topic
 ├── Partition 0 → Consumer A
 ├── Partition 1 → Consumer B
 └── Partition 2 → Consumer C

Consumer Group:
Each partition is consumed by one consumer
within that group at a time.
  • Producer: publishes messages.
  • Topic: logical stream/category of messages.
  • Partition: ordered log segment that enables parallelism.
  • Consumer: reads messages.
  • Consumer Group: group of consumers sharing partitions for parallel processing.
Q3. What is an Offset?

An offset identifies a message position within a Kafka partition. Consumers track progress using offsets.

Q4. What if a Kafka message is processed twice?

Design the consumer operation to be idempotent. For example, store a unique event ID or business operation ID and reject/ignore a duplicate that was already successfully processed.

Interview: “I would not assume every message is processed exactly once. I would make the business operation idempotent and handle duplicates safely.”

Q5. What is at-least-once delivery?

The message can be delivered more than once, so consumers must tolerate duplicates. It is often a practical reliability model for business systems.

Q6. How would Kafka fit a ride-hailing system?

   ↓ publish RideAccepted
Kafka Topic
   ├── Notification Service
   ├── Analytics Service
   └── Other downstream services

Core ride state is persisted in the database; Kafka handles asynchronous downstream work.

8. MySQL & Database

Q1. What is an index?

An index is a data structure that helps the database find rows more efficiently for suitable queries. It can improve reads but adds storage and write/update overhead.

Q2. How do you investigate a slow query?
  1. Look at the query and filters.
  2. Use EXPLAIN to inspect the execution plan.
  3. Check whether useful indexes exist.
  4. Review joins, selected columns, row counts and filtering.
  5. Consider a composite/covering index where appropriate.
  6. Measure again after the change.
EXPLAIN SELECT *
FROM orders
WHERE user_id = ?
  AND status = ?;
Q3. What is a composite index?

An index over multiple columns, such as (user_id, status). Column order matters because the database optimizer can use the index according to its access pattern and index-prefix rules.

Q4. What is a transaction?

A transaction groups database operations into a unit with properties commonly described by ACID: Atomicity, Consistency, Isolation and Durability.

Q5. What is read/write splitting?
Application
   ├── WRITE → Primary
   └── READ  → Replica

It can increase read capacity, but replication lag means a recent write may not be immediately visible on a replica.

Q6. What is replication lag?

When a replica has not yet applied a recent update from the primary. A user may write data and immediately read from a lagging replica, seeing stale data.

Q7. What is database sharding?

Splitting data across multiple database nodes based on a sharding key to distribute storage and workload. Choosing a good key is critical to avoid hotspots and difficult cross-shard queries.

Honesty for you: Your CV does not explicitly claim production sharding experience, so describe it as knowledge unless you have real project experience.

Docker packages an application and its dependencies into a container image so it can run consistently across environments.

Q2. What is Kubernetes?

Know these terms: Pod, Deployment, Service, Replica, ConfigMap, Secret, health checks, scaling.

Q1. How would you design ride acceptance?
  1. Authenticate the driver.
  2. Validate the ride and driver eligibility.
  3. Acquire a distributed lock for the ride, if needed.
  4. Check that the ride is still AVAILABLE.
  5. Use a database transaction/conditional update to change it to ACCEPTED.
  6. Release the lock.
  7. Publish a RideAccepted event to Kafka.
  8. Downstream consumers handle notifications/analytics asynchronously.
  9. Use idempotency for retries and duplicate requests.
Q2. Where would you use Redis?

For low-latency cache data and potentially a distributed coordination mechanism such as a lock. The database remains the source of truth for critical ride state.

Q3. Where would you use Kafka?

For asynchronous events such as RideAccepted, notification events, analytics events and other decoupled downstream processing.

Q4. How would you prevent duplicate booking?

Combine concurrency control with database correctness: distributed lock where appropriate, conditional state transition/transaction in the database, and idempotency for repeated client requests.
